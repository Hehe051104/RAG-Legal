## 1. 系统概述

### 1.1 系统定位

本系统是一个基于检索增强生成（RAG）技术的中文法律智能问答系统。系统采用IRAC法律分析框架（Issue-Rule-Application-Conclusion），能够对用户提出的法律问题进行结构化分析，提供专业的法律意见。

### 1.2 核心能力

| 能力 | 描述 |
|------|------|
| **法律问答** | 支持刑法、民法、行政法等14个法律领域的专业问答 |
| **IRAC分析** | 自动识别法律问题、检索法律依据、进行法律推理、得出结论 |
| **混合检索** | 标签精准匹配 + 向量语义搜索 + 关系扩展的三路检索策略 |
| **溯源引用** | 每个回答附带法律条文和案例的溯源卡片，支持全文查看 |
| **多模态支持** | 支持文件上传（OCR识别）、语音合成（TTS）、语音识别（STT） |

### 1.3 数据规模

- **法律原文**: 26部法律的.docx文件
- **司法解释**: 9份司法解释的.docx文件
- **案例库**: 200+案例的.docx文件
- **向量库**: 约3000+条法律/案例记录的向量化存储

### 4.2 查询重写模块 (`src/RAG.py`)

#### 4.2.1 功能概述

将用户的自然语言问题转换为结构化的检索指令，提升检索精度。

#### 4.2.2 核心函数

**`rewrite_query(user_query, history, model_name)`**

- **输入**: 用户问题、对话历史、模型名称
- **输出**: 结构化搜索指令字符串
- **格式**: `领域:XXX|【法律名-第xxx条】|法律关键词:A、B、C|案例关键词:D、E、F`

**处理流程**:

```
用户问题
    │
    ▼
┌─────────────────────────────────────────┐
│  构建Rewrite Prompt                      │
│  - 注入可用法律清单 (registry.json)      │
│  - 注入对话历史                          │
│  - 包含Few-shot示例                      │
└─────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────┐
│  调用 Ollama LLM                        │
│  - num_ctx=4096                         │
│  - temperature=0.3                      │
└─────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────┐
│  解析输出                                │
│  - 提取领域、法律名、关键词              │
│  - 失败时回退到原始查询                  │
└─────────────────────────────────────────┘
```

**Prompt设计要点**:
- 提供`data/registry.json`中的完整法律/案例清单
- 包含丰富的Few-shot示例
- 明确的红线规则（禁止编造法律名称）
- 支持法律条文和案例号的精准识别

#### 4.2.3 IRAC生成

**`call_ollama_rag(query_text, retrieved_docs, history, model_name)`**

- **有法律依据时**: 使用IRAC框架Prompt
- **无法律依据时**: 简单对话Prompt

**IRAC Prompt结构**:
```
你是一位专业的中国法律分析师...

## 检索到的法律依据
{法律/解释文档}

## 检索到的案例
{案例文档}

## 分析要求
请按照IRAC框架进行分析：
1. Issue（争议焦点）: 识别核心法律问题
2. Rule（法律规则）: 引用相关法律条文
3. Application（法律适用）: 将规则应用于具体事实
4. Conclusion（结论）: 给出法律意见和风险提示
```

### 4.3 混合检索模块 (`src/search.py`)

#### 4.3.1 检索策略

系统采用三路混合检索策略，确保检索的准确性和全面性：

```
用户问题 (经查询重写)
        │
        ▼
┌───────────────────────────────────────────────────────────────┐
│                    第一路：精准标签匹配                        │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │  解析 【法律名-第xxx条】 或 【案例号】                   │ │
│  │  在metadata中精确匹配                                    │ │
│  │  匹配结果标记 method="精准点名"                          │ │
│  └─────────────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────────┐
│                    第二路：分类型向量搜索                      │
│  ┌─────────────────────────┐  ┌─────────────────────────────┐ │
│  │  法律关键词              │  │  案例关键词                  │ │
│  │  → 向量搜索             │  │  → 向量搜索                 │ │
│  │  → doc_type=law_interp  │  │  → doc_type=case            │ │
│  │  → method="法律检索"    │  │  → method="案例检索"        │ │
│  └─────────────────────────┘  └─────────────────────────────┘ │
└───────────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────────┐
│                    第三路：关系扩展                            │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │  从 reverse_references.json 读取关联索引                 │ │
│  │  - 命中法律但无案例 → 补充关联案例                       │ │
│  │  - 命中案例但无法律 → 补充关联法律/解释                  │ │
│  └─────────────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────────────┘
        │
        ▼
    合并去重结果
```

#### 4.3.2 向量搜索实现

**`_vector_search(query_text, n_results, doc_type_filter)`**

```python
# 核心算法
1. 使用SentenceTransformer将查询文本向量化
2. 计算与所有文档向量的余弦相似度
3. 使用np.argpartition高效取top-k
4. 按source_article_number去重
```

**性能优化**:
- 向量预加载为float32 numpy数组
- 使用`np.argpartition`而非全排序
- 懒加载全局单例模式

#### 4.3.3 精准标签解析

**`parse_precise_tag(tag_text)`**

支持的格式:
- `刑法-第十条`
- `刑法 第十条`
- `刑法第十条`
- `指导案例1号`
- `（2023）最高法民申1234号`
- `案例-张某故意杀人案`

### 4.4 重排序模块 (`src/rerank.py`)

#### 4.4.1 两轮重排序策略

**第一轮：相关性评分**

```
检索结果列表
    │
    ▼
┌─────────────────────────────────────────┐
│  CrossEncoder 评分                       │
│  - 对每个 (query, content) 对打分        │
│  - 精准点名文档 → score=999 (VIP)       │
│  - 过滤 score < threshold 的文档         │
└─────────────────────────────────────────┘
    │
    ▼
  评分结果列表
```

**第二轮：类型均衡选择**

**`_type_balanced_select(scored_docs, top_n)`**

```
评分结果列表
    │
    ▼
┌─────────────────────────────────────────┐
│  分离VIP文档 (score>=999)               │
└─────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────┐
│  普通文档按类型分组                      │
│  - law_docs: 法律/解释                  │
│  - case_docs: 案例                      │
└─────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────┐
│  均衡选择策略                            │
│  1. 至少1条法律/解释                     │
│  2. 至少1条案例                          │
│  3. 剩余名额按分数填充                   │
└─────────────────────────────────────────┘
    │
    ▼
  最终top_n结果
```

#### 4.5.2 认证流程

**邮箱注册流程**:

```
1. 用户提交邮箱 → POST /api/auth/send-code
   │
   ├─ 检查邮箱未注册
   ├─ 60秒防抖检查
   ├─ 生成6位验证码 (secrets.randbelow)
   ├─ HMAC-SHA256摘要存储
   └─ 异步发送验证邮件
   
2. 用户提交注册信息 → POST /api/auth/register
   │
   ├─ 验证验证码
   ├─ Argon2哈希密码
   ├─ 创建用户 (默认tier="premium")
   ├─ 解析管理员角色 (ADMIN_EMAILS/INVITE_CODE)
   └─ 发送欢迎邮件

3. 用户登录 → POST /api/auth/login
   │
   ├─ 查找用户
   ├─ 验证密码哈希
   └─ 生成JWT (HS256, 120分钟有效期)
```

**Google OAuth流程**:

```
1. 前端获取Google ID Token
   │
   ▼
2. POST /api/auth/google {credential}
   │
   ├─ 验证Google Token (google.oauth2.id_token)
   ├─ 检查audience/issuer
   ├─ 查找或创建用户
   └─ 生成JWT
```


- **签名算法**: HS256

```
章 (一、关于一般规定)
  └─ 条 (第一条)
```

#### 4.6.3 案例解析

**`parse_case(file_path, output_json)`**

处理策略:
- 短文档(<2000字): 合并为一条记录
- 长文档: 按段落结构拆分（本院认为、经审理查明等）

## 10. 关键设计决策

### 10.1 双数据库架构

**决策**: 后端使用SQLite存储用户/认证数据，前端使用PostgreSQL存储聊天历史/文档。

**原因**:
- SQLite轻量级，适合单机部署的认证系统
- PostgreSQL支持原chatbot-ui的复杂查询需求
- 法律助手的对话历史仅在前端localStorage中，无需后端持久化

### 10.2 自建向量存储

**决策**: 使用numpy矩阵（embeddings.npy + metadata.json）而非ChromaDB。

**原因**:
- 数据规模较小（约3000条），numpy足够高效
- 避免ChromaDB的额外依赖和复杂性
- 便于调试和理解底层实现

### 10.3 三路混合检索

**决策**: 标签精准匹配 + 分类型向量搜索 + 关系扩展。

**原因**:
- 标签匹配: 支持用户精准引用法律条文
- 分类型搜索: 确保法律和案例两类文档都有代表性
- 关系扩展: 补充关联的法律/案例，提升回答完整性

### 10.4 IRAC框架

**决策**: 要求LLM输出结构化的IRAC JSON分析。

**原因**:
- IRAC是法律分析的标准框架，符合法律专业人士的思维模式
- JSON格式便于前端结构化渲染
- 降级策略确保系统鲁棒性

### 10.5 认证代理模式

**决策**: 认证接口通过Next.js代理转发，核心接口直接跨域请求。

**原因**:
- 认证接口需要设置HttpOnly Cookie，必须同源
- 核心接口直接请求后端，减少代理延迟
- CORS白名单控制跨域访问安全

### 10.6 SSE流式响应

**决策**: 使用Server-Sent Events实现流式响应，每4字符发送一次delta。

**原因**:
- 提升用户体验，实时显示生成过程
- 4字符粒度平衡了实时性和网络开销
- done事件携带完整references和irac，确保数据完整性
